## Run & Operate

- Managed artifact workflows run the web/API; do not start root `pnpm dev`.
- `pnpm run typecheck` — libs first, then artifact checks; `pnpm run build` — checks and builds.
- `pnpm --filter @workspace/finance-core run test` and `pnpm --filter @workspace/api-server run test` — foundation tests.
- `pnpm --filter @workspace/api-spec run codegen` — regenerate clients/Zod from OpenAPI.
- `pnpm --filter @workspace/db run push` — apply schema changes in development only, after reviewing changes; never use push-force for Prompt 2.
- `pnpm --filter @workspace/api-server run test` includes an isolated real-PostgreSQL finance concurrency/idempotency test when `DATABASE_URL` is set; it uses synthetic users/accounts and cleans them up.
- `DATABASE_URL` is required by the DB package when imported; API runtime requires workflow-provided `PORT` and `SESSION_SECRET` (at least 32 characters).

## Map & decisions

- `lib/finance-core` owns Money parsing, integer-minor-unit arithmetic, and Arabic/western-digit formatting; ILS/USD use 2 decimals, JOD uses 3. Use its exported `money`, `parseMoney`, `assertMoney`, `addMoney`, `subtractMoney`, `multiplyMoney`, `formatMoney`, `formatNumber`, `formatPercent`, `formatDate`. Never use floating-point arithmetic for financial amounts.
- App-owned auth was explicitly selected instead of Auth0. `users`, hashed opaque `sessions`, and `login_attempts` are persisted in PostgreSQL. Scrypt hashes use random 32-byte salts, N=32768/r=8/p=1, 64-byte keys. Session tokens are HMAC-SHA256 hashed with `SESSION_SECRET` at rest, seven-day `httpOnly`, SameSite=Lax, Secure-in-production cookie; sign-in rotates and logout revokes the session. `authorization.ts` receives only the verified server-side session principal. Specimen role previews never authorize requests.
- Every non-GET `/api` request requires a matching same-origin `Origin` header and `X-CSRF-Intent: 1` header; `customFetch` automatically supplies the CSRF header. API requests are same-origin with `/api` base URL. Generic invalid-credential errors, DB-backed attempt limits, no public admin signup/provisioning endpoint. Trusted operators can provision a new administrator with `pnpm --filter @workspace/api-server exec node scripts/provision-admin.mjs <email> '<display-name>'` in a private interactive terminal with DATABASE_URL configured; it prompts for a hidden password, refuses existing accounts, and never seeds credentials. Restrict command/database access to authorized operators.
- Contract: `POST /api/auth/signup` `{name,email,password,role:"student"|"parent"}`, `POST /api/auth/login` `{email,password}`, `GET /api/auth/me`, `POST /api/auth/logout`; account `{id,name,email,role,onboardingCompleted}`. `GET /api/profile` returns `{name,email,role,onboardingCompleted,education?,residence?,commute?,incomes:[],scholarships:[]}`. `PUT /api/profile` merges supplied `{name?,education?,residence?,commute?}` and `POST /api/profile/complete` validates student requirements. `POST/PUT/DELETE /api/profile/incomes[/:id]` and `/api/profile/scholarships[/:id]` create/update/delete owner-scoped records. GET profile is the canonical list for both. Full types and allowed enums are in `lib/api-spec/openapi.yaml`; generated clients and Zod validators live in `lib/api-client-react` and `lib/api-zod`.
- Profile money is **nonnegative integer minor units** `{minor,currency}` using finance-core ILS/USD (2 decimals), JOD (3 decimals). Commute estimate convention: trips/week × cost/trip × (2 if roundTrip) × 52 / 12, half-up rounding in minor units; overflow fails validation instead of losing precision. `manualEstimate=true` allows override; university/campus are only required for university students. Signup IP buckets count successes and failures (10 attempts per 15 minutes, 10th blocked), with old DB buckets pruned periodically. No money or income is posted to any account. Email verification/password reset are not operational until a mail provider is configured; UI must state this honestly and not claim mail was sent.
- `artifacts/api-server/src/middlewares/errors.ts` emits sanitized consistent errors after the existing health router. Unknown errors must not leak internals.
- `lib/db` is the DB source, `lib/api-spec/openapi.yaml` the contract, `lib/api-zod` and `lib/api-client-react` generated libraries. Preserve them until a feature explicitly changes them.
- Prompt 3 student home (`/`, `pages/account-home.tsx` → `components/home/*`) reads only `GET /api/profile`; no new endpoints. Pure exact-BigInt helpers in `src/features/home/student-home-model.ts` (tests: `node --experimental-strip-types --test src/features/home/student-home-model.test.ts`). Monthly income = active recurring incomes per currency (daily 365, weekly 52, biweekly 26, monthly 12, quarterly 4, yearly 1 per year ÷ 12, one rounding half-up); one_time/irregular excluded but dated entries listed as upcoming. School weekly allowance = annualised ÷ 52; irregular unknown. Next allowance = earliest active parent_allowance expectedDate ≥ today, else unknown. Balance, accounts (wallet/bank/cash/other), spending, bills, savings, campus activity and transactions render explicit not-available states until Prompt 4+ — never zeros. Parent/admin keep the simple summary with no family finance.
- Prompt 4 backend `/api/finance/*` and `/api/campus/*` is simulated only. Students create accounts at zero; balances change solely through atomic, per-account row-locked ledger postings. Exact account UUID recipient lookup reveals name/currency but not balance. Cross-student `send`, own-account `transfer`, explicit external `add/receive/deposit/withdrawal`, standalone `payment` (category `other`, simulated-payment receipt), pending requests with payer fulfillment/decline or issuer cancellation, and campus server-priced cart payments require `Idempotency-Key` on finance POSTs. Per-owner transactions, receipt snapshots, derived per-currency monthly summary/category totals and transactional outbox events are persisted; they are not budgets, forecasts or AI. Catalog university/campus/service/product config is admin-only. Admin accounts are provisioned via the trusted private operator command above, never public signup. `GET /api/campus/catalog` is available to students/admins; new installations have **no catalog** until an admin configures it or a student explicitly opts into `POST /api/campus/demo/install`, which installs persisted fictional Demo University/Demo Campus example services and clearly illustrative prices globally. No funds or credentials are seeded by demo installation. Disabled services/products cannot be charged; historical prices remain on receipts. There is no actual bank, QR, wallet or university integration. Exact generated hooks/DTOs and request flows: `.local/prompt4-api.md`.
- Prompt 5 transactions: backend contract in `docs/prompt5-api.md` (`GET /api/finance/history`, `/api/finance/history/filter-options`, `GET /api/finance/transactions/:id`). Frontend `/transactions` (first-class student nav) and `/transactions/:id` deep link. Filters (search debounced, category by University/School/Campus/legacy group, 10 semantic types, inclusive UTC date range, amount min/max as exact decimal→minor units with required currency, account, university, campus, parent transfer, goal) are server-side, AND-combined, synced to the URL query (page resets to 1 on change) and persisted through detail/back/reload; invalid URL filters do not query. Pure helpers + tests: `src/features/transactions/history-filters.ts` (`node --experimental-strip-types --test src/features/transactions/history-filters.test.ts`). Home recent activity and the Money receipt dialog link into details; Home "All activity" goes to `/transactions`. No transaction editing. Prompt 7 now populates `relatedGoalId` and `goalFundingSource` for real goal contributions, with owner-goal filter IDs/names. `relatedBudgetId`, `parentTransferId`, `recurringExpenseId` remain nullable/null; broad family and allowance transfers are not implemented.
- Prompt 6 planning: contract in `docs/prompt6-api.md` (`/api/planning`, budgets, recurring expenses, plan lines, commute override). Frontend `/plan` (student nav, implemented) shows per-currency monthly equation expected income − planned expenses − planned savings = projected remaining (signed, exact minor units, no FX), server-computed totals only. Weekly (UTC Mon–Sun) / monthly (UTC calendar month) category budgets CRUD with live ledger actualSpent/remaining and overspent state; budget limits are comparisons only, never added as expenses. Recurring expense CRUD with active toggle; fixed/variable/savings monthly plan lines CRUD across all planning categories. Priority per category+currency: manual lines > active recurring > profile housing (share else rent, utilities, internet)/commute baseline; persisted commute override replaces the profile commute estimate. Income = active recurring profile sources normalized monthly (estimate, not guaranteed); one-time/irregular listed separately; scholarships shown as metadata only. Upcoming dated items never create ledger postings; the ledger stays immutable. Plan query refetches every 15s/on focus and is invalidated by planning mutations, `useRefreshFinance` (finance/campus payments) and profile save. Home shows plan projected remaining linking to `/plan`. Exact helpers + tests: `src/features/planning/planning-math.ts` (`node --experimental-strip-types --test src/features/planning/planning-math.test.ts`).
- Implement future features contract-first, validate inputs and outputs, and authorize per resource; see `docs/architecture.md` for boundaries and suggested feature-module structure.
- Prompt 7 backend contract and policy: `docs/prompt7-api.md`. Unlimited `/api/goals` are owner-only; current derives from dedicated protected `goal_reserve` account holdings, hidden/blocked in ordinary finance paths. Student contributions atomically debit available and credit reserved, never increasing wealth or income. Parent-only `/api/parent/goals` funding requires a student-generated, hashed, expiring, single-use exact-goal invitation and authenticated parent redemption. Revocation removes access immediately; parent DTOs exclude student identity/accounts/notes/history. External parent funding is explicitly simulated. Completion is explicit and requires full funding; archive retains all reserve funds and receipts. Goal contribution credits count once in savings budgets. Planning uses max(manual savings envelope, summed active dated goal monthly requirements) per currency. Finance cashflow balance remains available, with additive reservedBalance/netBalance; transaction goal options now contain real owner IDs/names. No full parent dashboard/family access. New schema applied additively using non-force development DB push; isolated PostgreSQL tests cover concurrency, idempotency, consent, reserve isolation and planning/budget reconciliation.

## Constraints

Planning frontend helper paths and the standalone planning test command above are relative to `artifacts/student-financial-os`; run that test from that directory.

Prompts 2–7 scope only: no real bank/wallet providers, seeded credentials, broad family relationship features, full forecasting or AI features. Parent access is limited to explicitly consented goal funding, not Prompt 8. Maintain strict integer-money validation and sanitized error messages. Node 24, pnpm workspaces, TypeScript, Express 5, PostgreSQL/Drizzle, Zod and Orval are the existing stack.

Approved UI direction: calm, spacious, premium student fintech rather than a generic dashboard. The gold redesign supersedes the original indigo palette: signature gold `#D4A72C`, deep navy `#111827`, warm canvas `#FAF9F5`, white, primary text `#172033`, slate `#64748B`, calm green `#22A06B`, and red `#EF4444` for errors/critical or destructive states. Use semantic tokens and accessible derived shades; gold is a restrained interaction accent, not a universal fill. Inter + Noto Sans Arabic, 4px spacing, English/Arabic LTR/RTL, Light/Dark/System, WCAG 2.2 AA focus and reduced motion remain foundational constraints. Prefer open hierarchy/dividers over nested cards, gratuitous gradients, and decorative charts. A financial-home reference is permitted only as explicitly labeled design specimens with centralized static fixtures; never represent it as real financial activity or enable financial actions.
