# Prompt 8 backend contract

Contract source: `lib/api-spec/openapi.yaml`. Generate: `pnpm --filter @workspace/api-spec run codegen`.
All URLs below have `/api` prefix; generated hooks supply it. Real verified sessions and existing same-origin `Origin` + `X-CSRF-Intent: 1` guards apply. Never use student finance APIs for a parent. All wallet/allowance mutations require a fresh `Idempotency-Key` (8–128 permitted ASCII characters), reused for identical network retries only. Family consent mutations do not require that header. UUID path parameters, integer minor-unit amounts `{minor,currency:"ILS"|"USD"|"JOD"}`. Mutations reject unknown properties. No real payments or email delivery.

## Student consent prerequisite (only the approved early Prompt 9 slice)

- `useGetStudentFamily()` / GET `/family` → `{links:FamilyLink[],allowances:StudentAllowance[],projection:AllowanceProjection}`.
- `useCreateFamilyInvitation()` / POST `/family/invitations`, variables `{data:{permissions,receivingAccountId}}` → `{link,token}`. All eight boolean keys: `monthlySummary,balance,goals,allowance,requests,transactions,upcomingPayments,campusSpending`. Defaults are **false**. Student explicitly selects flags. `receivingAccountId` is student's own ordinary account UUID or null; allowance=true requires an account. Student may choose it from existing `useListFinanceAccounts()`.
- `useUpdateFamilyConsent()` / PUT `/family/links/{id}`, `{id,data:{permissions,receivingAccountId}}` → `FamilyLink`.
- `useRevokeFamilyLink()` / DELETE `/family/links/{id}`, `{id}` → 204. Revocation is terminal. Removing allowance consent cancels active/paused schedules, retains history; re-enabling never revives them.
- `FamilyLink` has `id,status:"pending"|"accepted"|"declined"|"revoked",permissions,receivingAccountId,createdAt,expiresAt`, and **only when accepted** `parentName`.
- Copy token privately once (32 random bytes/base64url, hash-only at rest, seven-day acceptance expiry). No email sent. Do not put tokens in URLs, logs or localStorage.
- `useDecideFamilyInvitation()` / POST `/parent/family-invitations/decide`, `{data:{token,action:"accept"|"decline"}}` → `{status:"accepted"|"declined",childId?,childName?}`. Authenticated parent only. Names/child ID appear only after acceptance. Declining reveals neither. Single-parent binding; repeated identical decision by the same parent is safe. Multiple guardians/children supported, one current accepted link per pair.

## Parent APIs

- `useGetParentDashboard()` / GET `/parent/dashboard` → `{children:ParentChild[],simulated:true,requestsStatus:"coming_soon",goalFundingPath:"/goals/fund"}`.
- `useGetParentChild(childId)` / GET `/parent/children/{childId}` → `ParentChild`.
- `ParentChild` always has `{childId,name,permissions}` for an accepted link. Optional **omitted, never zero-filled or frontend-only hidden** sections:
  - `balance:Amount[]` only balance permission (available accounts, excludes goal reserves).
  - `monthlySummary:[{currency,income,spending,campusIncluded}]` and `income:Amount[]` only monthlySummary permission; income is actual current UTC month's ledger credits excluding generic transfers/internal goal transfers.
  - `transactions:[{id,type,amount,direction,createdAt}]` only transactions permission. No notes, counterparties, account IDs, balanceAfter, receipt items or campus metadata.
  - `campusSpending:Amount[]` only campusSpending permission.
  - `goals:ParentFundingGoal[]` only goals permission, read-only summaries; **not funding permission**. Existing `/goals/fund` and original exact-goal consent still required for Prompt 7 funding. Funding remains simulated external; it does not debit the new wallet.
  - `allowances:Allowance[]` only allowance permission, only this parent's schedules.
  - `allowanceCurrency:"ILS"|"USD"|"JOD"` only allowance permission: currency of the student's selected receiving account. Frontend allowance forms must use this currency and offer only same-currency parent accounts. This field exposes **neither receiving account ID nor balance**, including when balance permission is denied. It is omitted entirely when allowance permission is denied.
  - `upcomingPayments:[{id,date,amount,source:"allowance"|"recurring"|"income"|"line"}]` only upcomingPayments permission.
  - `requests:{status:"coming_soon",items:[]}` only requests permission. No parent request records exist in earlier prompts; peer requests are never duplicated. Approval/ask-details/notification workflows deferred to Prompt 9.
- Without campusSpending, campus rows are excluded from transactions and monthlySummary **before aggregation**. Family activity deliberately excludes merchant descriptions/free text even with campus permission. Denied sections are not queried through frontend finance hooks.
- Planning aliases lose campus provenance when persisted (`cafeteria→food`, `bookstore→books`, `campus_transportation→transportation`, `fees→university_fees`). Without campusSpending, parent upcoming recurring expenses/plan lines conservatively omit these canonical campus-capable categories and their aliases. This can also hide non-campus items in those categories; it never changes the student's stored planning data, own planning response, or calculations.
- `useGetParentWallet()` / GET `/parent/wallet` → `{accounts:FinanceAccount[],transactions:FinanceTransaction[],simulated:true}` (own latest 100 ledger entries).
- `useCreateParentAccount()` / POST `/parent/wallet/accounts`, `{data:{type:"wallet"|"bank"|"cash"|"other",name,currency}}` → zero-balance `FinanceAccount`.
- `useTopUpParentWallet()` / POST `/parent/wallet/topups`, `{data:{accountId,amount,simulatedFundingAcknowledged:true}}` → own `FinanceTransaction`. Label **Simulated external top-up — no bank connection or real money**.

## Allowances

- `useListChildAllowances(childId)` / GET `/parent/children/{childId}/allowances` → `Allowance[]`.
- `useCreateAllowance()` / POST same path, `{childId,data:AllowanceInput}` → `Allowance`.
- `useUpdateAllowance()` / PUT `/parent/children/{childId}/allowances/{id}`, `{childId,id,data:AllowanceInput}` → `Allowance`.
- Editing applies only to active/paused schedules, never to posted history. An unresolved failed occurrence must be retried or explicitly cancelled (then create a replacement schedule), not silently skipped/repriced by editing. A future date cannot rewind to any previously posted/cancelled occurrence.
- `AllowanceInput` requires every field: `{parentAccountId,amount,kind:"oneTime"|"recurring",frequency:"weekly"|"biweekly"|"monthly"|null,nextPayment:"YYYY-MM-DD",startDate:"YYYY-MM-DD",endDate:"YYYY-MM-DD"|null,note:string}`. One-time uses frequency=null and startDate=nextPayment (the date); recurring uses non-null frequency. Amount positive safe integer, note ≤500 chars. Start/end inclusive; nextPayment inside interval; creation/edit nextPayment cannot be in the past. Accounts must be same currency; no FX. Receiving account is selected by student consent, never by parent.
- `useChangeAllowanceStatus()` / POST `.../{id}/status`, `{childId,id,data:{action:"pause"|"resume"|"cancel"}}` → `Allowance`.
- `useRetryAllowance()` / POST `.../{id}/retry`, `{childId,id,data:{retry:true}}` → `Allowance`. Attempts one current due occurrence, also useful to process a newly created today-due allowance immediately. Use a **new key for each deliberate retry after top-up**. Inspect returned `lastFailure`, not just HTTP success.
- `Allowance` = input + `{id,childId,status:"active"|"paused"|"cancelled"|"completed",lastFailure:"insufficient_funds"|"balance_limit"|null,occurrences:AllowanceOccurrence[],createdAt}`.
- `AllowanceOccurrence` = `{id,scheduledDate,amount,status:"posted"|"failed"|"cancelled",failure:"insufficient_funds"|"balance_limit"|null,transactionIds:string[],attemptedAt}`. Stable unique schedule+date occurrence ID; failed retry reuses same occurrence. Posted amounts/receipts immutable.
- Student `StudentAllowance` omits parent's account ID and child identity; otherwise includes input schedule fields, status/failure/history. Student occurrence ledger IDs are restricted to student's own credit.
- Background server lifecycle worker runs immediately and every 30s, with bounded batches. No workflow/cron setup needed. Active schedules process at most one occurrence per pass; up to 50 schedules per pass. Explicit insufficient-funds/overflow failures persist and stop automatic catch-up for that schedule until parent retry. No silent lost payment. Cancellation/revocation prevent future postings; pause retains pending date for bounded catch-up after resume.
- Weekly/biweekly are UTC calendar-day increments; monthly uses original start-day anchor clamped to month-end (Jan 31 → Feb 28 → Mar 31). End date inclusive. One-time or final recurring occurrence sets completed.

## Income / planning reconciliation and freshness

Posted allowance is ledger `kind:"allowance",category:"parent_allowance"`: student credit is real simulated income, parent debit reduces wallet. Both ledger legs share `parentTransferId` = occurrence UUID. Not generic transfer (which cashflow excludes). Never insert or edit onboarding income rows. Ledger actuals and expected-income forecasts are separate; do not add posted actuals to forecasts.

`AllowanceProjection` is available on GET `/family`, additive `profile.allowanceProjection`, and additive `financialPlan.allowanceProjection`:
`{policy:"inclusive_parent_allowance_envelope",totals:[{currency,manualMonthly,scheduledMonthly,effectiveMonthly,adjustmentMonthly}],upcoming:[FamilyUpcoming]}`.
Active consented recurring schedules whose start date has arrived and end date has not passed contribute monthly estimates. One-time schedules appear upcoming only, not recurring totals. Paused/cancelled/completed/revoked schedules contribute nothing. Failed active schedules remain clearly estimates, not guaranteed income.

Safe explicit reconciliation: existing active recurring manual `parent_allowance` profile rows represent an **inclusive allowance envelope**. Per currency use `max(manual annual numerator, scheduled annual numerator)`, not their sum. Other income is added normally, then one half-up rounding per currency. `adjustmentMonthly` is the exact difference between full projected income with/without schedule reconciliation; add only this field to an existing home calculation based on profile incomes. `effectiveMonthly` describes the allowance envelope alone, not all income. This policy does not delete, replace, deactivate or silently overwrite user rows; display an explanation and direct users to edit their manual envelope if needed. Multiple genuine guardian schedules are summed before comparing to the envelope.

Existing GET `/planning` authoritative totals incorporate this exact reconciliation and include allowance upcoming entries (source `income`). Student planning and parent upcoming use the same shared dated reconciliation rule: replace a manual `parent_allowance` upcoming expectation **only when a visible active scheduled occurrence has exactly the same currency and expected date**, inside its start/end interval and not past its end date. Different dates/currencies remain visible. Monthly forecast envelope reconciliation above is unchanged and independent of this dated-list deduplication. Parent upcoming considers only that parent's own schedules and only with allowance consent; without allowance consent, no schedules are queried/disclosed and manual expectations remain visible under upcomingPayments permission. Overdue active occurrences may remain visible as due obligations; they never suppress a future manual expectation. Goals savings reconciliation remains unchanged. Budget actuals unchanged: allowances are income, not expense/savings.

Refetch parent dashboard/child/allowances/wallet and student family/profile/finance summary/history/planning every 15–30s + on focus/mount. Invalidate those affected keys after mutations, clear caches on account change. Every query hook has generated `get<OperationName>QueryKey` (e.g. `getGetParentDashboardQueryKey()`, `getListChildAllowancesQueryKey(childId)`). Hook success values are direct payloads, no envelope. Permission revocation may turn child queries into 404; remove stale display. Keep unavailable vs denied vs empty distinct.
