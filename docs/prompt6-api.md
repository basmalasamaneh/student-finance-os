# Prompt 6 planning API handoff

Source contract: `lib/api-spec/openapi.yaml`. Generated with `pnpm --filter @workspace/api-spec run codegen`; import DTOs/hooks from `@workspace/api-client-react`. Student session required on all `/api/planning` endpoints. Mutation requests require same-origin Origin and `X-CSRF-Intent: 1` (existing generated fetcher). No userId or balance is accepted from clients.

- `useGetFinancialPlan()` returns `FinancialPlan`: `asOf`, `estimate:true`, `policy`, `totals[]`, `costs[]`, `income[]`, `irregularIncome[]`, `irregularCount`, `upcoming[]`, `budgets[]`, `budgetCounts:{weekly,monthly}`, `recurringExpenses[]`, `lines[]`, `housing?`, `commute?`, `scholarships[]`, `commuteOverride`. `totals[]` contains a currency row for each currency represented in any owner profile/income/budget/recurring/line record, including a zero total when only an excluded irregular income or budget exists; an untouched owner has `totals:[]`. Use `getGetFinancialPlanQueryKey()` to invalidate after all planning mutations, profile/income changes and campus/finance payments. Also refetch on focus/mount for other-session payments.
- `useCreateBudget()`, `useUpdateBudget()`, `useDeleteBudget()`: mutations take `BudgetInput {category,period:"weekly"|"monthly",limit:{minor,currency}}`; updates/deletes take UUID `id`. One budget per owner/**canonical** category/period/currency (aliases cannot create duplicates; duplicate 409). Response `Budget` includes live `actualSpent`, signed `remaining`, `periodStart`, `periodEnd`. Weekly = UTC Monday through Sunday; monthly = UTC calendar month. Only debit payments/withdrawals (not sends/transfers) count; aliases consolidate `cafeteria→food`, `bookstore→books`, `campus_transportation→transportation`, `fees→university_fees`, `rent/accommodation→housing`. A ledger debit contributes once per budget period/category/currency. Weekly and monthly budgets are independent comparisons; never sum their actuals or limits.
- `useCreateRecurringExpense()`, `useUpdateRecurringExpense()`, `useDeleteRecurringExpense()` use `RecurringExpenseInput {category,amount,frequency,nextDate,description,active}`. Dates are strict ISO calendar dates; active schedules with a future/current next date surface in `upcoming` without creating ledger debits. The server never advances the next date automatically.
- `useCreatePlanLine()`, `useUpdatePlanLine()`, `useDeletePlanLine()` use `PlanLineInput {category,type:"fixed"|"variable"|"savings",amount,description,upcomingDate?}`. `savings` type requires `category:"savings"` and non-savings types forbid it. Each line is a monthly estimate; optional `upcomingDate` is informational only.
- `useSavePlanCommuteOverride()` takes `{enabled:false}` or `{enabled:true,amount}`. Setting is persisted separately from the profile. Enabled override replaces profile commute estimate, never charges an account. Profile housing/commute edits use existing `useSaveProfile()`; `housing` and `commute` on plan show those persisted profile values.

All amounts are exact integer minor units (ILS/USD 2 decimals, JOD 3), `0..MAX_SAFE_INTEGER`; `remaining` and `projectedRemaining` use separate signed `SignedAmount` schema. No FX conversion or invented exchange rate. `totals[]` are per currency; negative remaining is possible. Income is normalized from all active recurring onboarding income sources (365/52/26/12/4/1 annual occurrences, sum annual numerators **per currency**, divide by 12, half-up **once** as Prompt 3 does). Each `income[].monthlyEstimate` is independently rounded for display and may differ from the per-currency total by a minor unit; use `totals[].expectedIncome` as authoritative. Likewise recurring expense numerators are summed and rounded once per category/currency. One-time/irregular are excluded from expected monthly income and listed separately. Active income with an expected date, including recurring sources, is shown in `upcoming` but is not summed again. Scholarships are profile metadata and not summed a second time.

Planning expense priority per **category and currency**: manual expense line(s) replace recurring entries and profile baseline in that category/currency; otherwise active recurring entries replace profile baseline; otherwise profile housing/commute baseline is used. Multiple manual lines or recurring entries in the same bucket sum together. Housing baseline uses studentShare if available, else monthlyRent, plus utilities and internet as distinct categories; `housing`, `utilities`, `internet`, `transportation` can each be replaced independently. Budget limits are comparison thresholds ONLY, not planned expenses. Savings lines only count in planned savings. All cost sources and `policy` make the priority visible. No automatic ledger posting, goals, parent links or real bank interactions.

The additive `planning_budgets`, `planning_recurring`, `planning_lines` and `planning_settings` tables were applied to the development database with non-force `pnpm --filter @workspace/db run push`. Deploy the additive schema before the API. Backend tests: `pnpm --filter @workspace/api-server run test` (real PostgreSQL owner-scoped planning, live campus ledger spending, precision and precedence) and `pnpm --filter @workspace/api-server run typecheck`.
