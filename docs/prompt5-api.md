# Prompt 5 backend/frontend API handoff

Prompt 7 extension: `relatedGoalId` is now populated on savings contribution ledger entries; `goalFundingSource` distinguishes `student_account` and `parent_simulated`. Filter options contain real owner goal IDs plus additive `goalOptions:[{id,name}]`. Other future relationship fields remain nullable. The original Prompt 5-only exclusions below describe historical scope; see `docs/prompt7-api.md`.

Source of truth: `lib/api-spec/openapi.yaml`. Generated with `pnpm --filter @workspace/api-spec run codegen`; import hooks and DTOs from `@workspace/api-client-react`. All calls use the existing session and `/api` base URL. Student role required.

## Generated hooks

- `useGetFinanceHistory(params?)` → `FinanceHistoryPage { items: FinanceTransaction[], page:number, limit:number, total:number, hasMore:boolean }`. Cache key: `getGetFinanceHistoryQueryKey(params)`. Ordered newest first by `createdAt DESC, id DESC`. Defaults `page=1`, `limit=20` (max 100). No matches: `items:[], total:0, hasMore:false`.
- `useGetFinanceHistoryFilterOptions()` → `FinanceHistoryFilterOptions { categories, accounts, universities, campuses, goals }`. Cache key: `getGetFinanceHistoryFilterOptionsQueryKey()`. Categories are static bilingual complete university/school/campus lists even with no records. Accounts are owner accounts; campus/university options are derived only from the owner's actual campus transaction history, **not** the global catalog. Goals is `[]` until goals are implemented.
- Existing `useGetFinanceTransaction(id)` → full owner-only `FinanceTransaction` detail, 404 for inaccessible IDs. Existing `useListFinanceTransactions()` remains the unfiltered latest 100 items for legacy callers; use history for pagination and filters. `useGetFinanceSummary()` retains its original contract and calculation. List, summary recent/campus items, details, history, and movement/campus receipts now use the same owner-scoped contextual enrichment. An owner-owned counterparty account may be named; another student's account remains anonymous.

`GetFinanceHistoryParams` has optional `search`, `category`, `type`, `dateFrom`, `dateTo`, `amountMin`, `amountMax`, `amountCurrency`, `accountId`, `parentTransferId`, `campusId`, `universityId`, `goalId`, `page`, `limit`. Dates are `YYYY-MM-DD` inclusive UTC calendar dates. Amount bounds use **integer minor units** (`0..Number.MAX_SAFE_INTEGER`) and require `amountCurrency` (`ILS|USD|JOD`); reversed bounds are invalid. Search is a trimmed nonblank string (max 120), matching note, merchant, account name, stored kind/category, semantic type. All filters combine with AND. Malformed dates, duplicated/unknown params, invalid UUIDs, unsafe money and invalid ranges return 400. Cross-owner IDs yield no rows and never expose another user's entries.

`FinanceTransaction` preserves original fields (`id`, `accountId`, `kind`, `category`, `direction`, `amount`, `balanceAfter`, `status`, `createdAt`, optional `counterpartyAccountId`, `serviceId`, `merchantName`, `items`, `note`). Added required `userId`, semantic `type`, `description`, `source:string|null`, `destination:string|null`, and nullable `relatedGoalId`, `relatedBudgetId`, `parentTransferId`, `campusServiceId`, `universityId`, `campusId`, `recurringExpenseId`. Optional `accountName`, nullable `universityName` and `campusName` provide contextual labels. `amount` and `balanceAfter` remain `{minor,currency}`. `source`/`destination` are contextual simulated labels, not verified bank identities; other-student names are not exposed.

Semantic types: `income | expense | transfer | allowance | refund | savings | withdrawal | deposit | payment | campus_payment`. Distinguish historical storage `kind`: `add`/`receive` credit → `income`; `send`, `transfer`, fulfilled requests → `transfer`; standalone payment → `payment`; service-backed payment → `campus_payment`. Future `allowance`, `refund`, `savings` are representable but are **not** posted by an arbitrary transaction editor. No new ledger mutation route exists. No balances or ledger history were rewritten.

## Filter/category mapping

`categories` entries: `{group:"university"|"school"|"campus"|"legacy",key,label,arabicLabel}`. Render localized labels, send the **key**. Full University (21), School (8), Campus (6) taxonomies are returned even when unused. Stored Prompt 4 categories persist unchanged: `external_income`, `external_outflow`, `transfer`, `other`, and service `food`, `books`, `printing`, `transportation`, `fees`, `other`. `legacy` covers non-taxonomy values. For campus payments, filter key `cafeteria` includes stored campus `food`; `bookstore` includes `books`; `campus_transportation` includes `transportation`; `university_fees` includes `fees`; `other_campus` includes `other`. Filters for `food`/`books` match exact stored values in any context. Display group/context appropriately; do not pretend old records were recategorized.

Campus payment checkout now persists trusted university/campus IDs and English name snapshots from server catalog. Legacy service-backed receipts resolve IDs/names through the stored service relationship when it still exists. Receipt merchant, purchased items and prices remain immutable. Unknown historical context remains null. Unimplemented `relatedGoalId`, `relatedBudgetId`, `parentTransferId`, `recurringExpenseId` remain null; those filters correctly yield no results. No family or budget relationships are fabricated.

Development DB migration: additive nullable columns were applied with non-force `pnpm --filter @workspace/db run push`. Apply the same additive schema change in other deployments **before** deploying the API. Existing Prompt 4 mutations retain their CSRF and idempotency requirements.
