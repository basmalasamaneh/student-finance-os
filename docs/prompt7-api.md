# Prompt 7 savings goals API handoff

**Backend implemented:** OpenAPI, generated hooks/DTOs, authenticated routes, protected reserves, planning/budget/ledger integrations and isolated PostgreSQL tests are implemented. Source: `lib/api-spec/openapi.yaml`; generate with `pnpm --filter @workspace/api-spec run codegen`. This is Prompt 7 only, not a parent dashboard or banking integration.

## Student API / generated hooks

All `/api/goals` endpoints require a verified **student** session. Existing same-origin Origin and `X-CSRF-Intent: 1` requirements apply. All goal create/edit/status/contribution mutations require an `Idempotency-Key` (8–128 permitted ASCII characters; reuse only for identical retries). Supply through generated hook request options, as with finance. Invitation creation intentionally does not persist an idempotent plaintext token response.

- `useListSavingsGoals()` → `SavingsGoalsOverview {goals,totals,activeCount,completedCount,policy}`. Includes every owner goal, including archived. No arbitrary maximum number of goals. `totals[]` is per currency: `available`, `reserved`, `netBalance`, `requiredContributionMonthly`. Archived/completed holdings remain in reserved totals; never spendable balance.
- `useCreateSavingsGoal()` → `{data:SavingsGoalInput}` returns `SavingsGoal`. Input is `{name,target:{minor,currency},targetDate:string|null,category,priority:"low"|"medium"|"high",notes}`. Category is a real user-entered label (1–80 chars). Name 1–120; notes up to 2000. All input fields required, including nullable date and possibly empty notes. Target is strictly positive. Currency is chosen inside target; never submit current, status, percentage or estimates.
- `useGetSavingsGoal(id)` → full owner `SavingsGoal`.
- `useUpdateSavingsGoal()` → `{id,data:SavingsGoalInput}` full replacement of editable metadata. Target cannot fall below current; currency cannot change once funded. Completed/archived goals cannot be edited.
- `useChangeSavingsGoalStatus()` → `{id,data:{action:"pause"|"resume"|"complete"|"archive"}}`. Active→paused, paused→active; active/paused→completed only when fully funded; active/paused/completed→archived. Archive is terminal. Repeating an already-applied action with the same idempotency key replays its receipt. No delete, withdrawal or implicit release.
- `useContributeToSavingsGoal()` → `{id,data:{accountId,amount:{minor,currency},note?}}` returns `GoalContributionReceipt {goal,entry,transactions}`. Only active goals; strictly positive same-currency contributions, no overfunding. Account must be an ordinary owner account with available funds. Two immutable linked ledger entries (ordinary debit + protected reserve credit), one contribution history event. Exact-target funding **does not auto-complete**; user explicitly completes, and remaining/required saving becomes zero meanwhile.
- `useGetSavingsGoalHistory(id)` → `GoalHistoryEntry[]`, newest first. Event fields: `id,goalId,action,source,amount,transactionIds,note,createdAt`. Status/metadata events have null amount/source and empty ledger links. Student contribution links both ledger legs; parent contribution links the reserve credit. Owner history includes both sources.

Goal DTO adds `id,currency,current,status,percentage,remaining,requiredContributionMonthly,estimatedCompletion,createdAt,updatedAt`. All amounts use exact integer minor units (ILS/USD 2 decimals, JOD 3), `0..MAX_SAFE_INTEGER`. Financial calculations use BigInt; only checked safe integers cross JSON. Percent is a presentation number rounded down to two decimals using integer basis points, never used in money arithmetic.

## Narrow parent consent — not family access

1. Student explicitly accepts disclosure: **“Allow one signed-in parent to see this goal's name, target, saved amount, remaining, target date and status, and add simulated funds. This does not share your accounts, profile, notes or other goals.”**
2. `useCreateGoalInvitation()` → `{id,data:{limitedConsentAcknowledged:true}}`; returns `{invitation,token}`. Token: at least 32 cryptographically random bytes, base64url; hash only at rest; seven-day expiry; single-use. Show/copy token privately once. No email is sent. Never put token in URL/query/log/localStorage, and do not retain it after dismissing the share view.
3. Parent signs into their actual **parent** account. `useRedeemGoalInvitation()` → `{data:{token,limitedConsentAcknowledged:true}}`; parent-only. Token redemption binds the authenticated principal to exactly that goal. Same parent retry is safe; another parent cannot reuse it. Invalid/expired/revoked/unavailable token errors disclose no goal information.
4. `useListParentFundingGoals()` → `ParentFundingGoal[]` with ONLY `id,name,target,current,remaining,status,targetDate`. This is the narrow funding screen, not Prompt 8. No student identity, balance/account IDs, profile, notes, global goals, or student history. Redeemed access persists until revoked; expiry limits redemption only.
5. `useFundSavingsGoalAsParent()` → `{id,data:{amount,simulatedFundingAcknowledged:true,note?}}` plus idempotency header. Returns `ParentGoalContributionReceipt {id,goal,amount,source:"parent_simulated",createdAt}`. Explain **“Simulated external funding — no bank connection or real money transfer.”** Creates only a reserve credit, never debits the student's available account. The authenticated parent supplies provenance; no client userId or role selection can authorize it.
6. Student `useListGoalInvitations(id)` gets token-free invitations with `id,goalId,expiresAt,redeemedAt,revokedAt,createdAt`. `useRevokeGoalInvitation()` → `{id,invitationId}` revokes both token and any redeemed grant immediately. Repeat revoke is safe. Existing funds/receipts are retained; revocation cannot undo a contribution. Each request, including idempotent parent retries, must recheck current consent.

All resource IDs are UUIDs. Role violations 403, no session 401, inaccessible owner resources 404, malformed input 400, invalid transitions/overfunding/idempotency mismatch 409, insufficient funds use the existing finance error. Strict inputs reject unknown identity/balance fields.

## Money / forecast / budget invariants

- A dedicated protected reserve account backs each goal. `current` is derived from that holding, not a mutable counter. Reserve accounts are excluded from ordinary account lists/recipient lookup and denied by every ordinary movement/request/campus payment path. Goal savings change liquidity, not net wealth.
- Student reserve debit+credit is internal, never income or spending twice. Parent reserve funding is clearly simulated external income in ledger cashflow, not onboarding expected income and never a fabricated student transfer.
- Existing finance cashflow `balance` means **available**, with additive `reservedBalance` and `netBalance`. `netBalance = available + reserved`; goal overview totals are authoritative for goal UI. No currency conversion or cross-currency sum.
- Savings budget actuals count each contribution once via the reserve credit, including parent contributions. The paired ordinary debit is not counted again. Existing non-savings budget rules remain unchanged. Weekly/monthly comparisons still overlap, so never sum their actuals.
- Active dated goals require `ceil(remaining / months)` per month, where months is inclusive UTC calendar months from today through deadline, minimum one for an overdue/current-month deadline. Required amount null for undated/inactive goals; do not invent a deadline. Paused/archived/completed goals have no forecast requirement.
- Estimated completion is null without meaningful actual contribution history: require at least two contributions on different UTC days. Pace uses contributions after the first over elapsed time from first contribution through now; use exact ceiling to project remaining days. Inactive goals have null estimate. Fully funded active goals show actual final-contribution date. No synthetic dates based on default saving rates.
- Planning adds `goalSavings[] {currency,goalRequired,manualSavings,effectiveSavings,undatedActiveCount,policy:"maximum_manual_or_goals"}`. Per currency, `effectiveSavings = max(manual monthly savings total, active dated goal requirements total)`, not their sum: manual savings is treated as an inclusive overall envelope; goals establish its floor. This prevents manual lines earmarked for goals from counting twice without hiding required contributions. `totals[].plannedSavings` uses effective savings. Undated goals remain visibly unforecasted. Expenses and profile expected income unchanged.
- History `goals:string[]` remains compatible and becomes real owner IDs; additive `goalOptions:[{id,name}]` supplies labels. Transactions add `goalFundingSource` provenance and `relatedGoalId`, with immutable receipts and transactional outbox events.
- Goal/account row locks, stable account ordering and existing transaction-scoped idempotency protect concurrent overspending, overfunding and duplicate requests. Consent changes and parent funding serialize on the goal lock. Failed operations leave no partial holdings/history/ledger changes.

## UI freshness

Use generated `getListSavingsGoalsQueryKey`, `getGetSavingsGoalQueryKey(id)`, `getGetSavingsGoalHistoryQueryKey(id)`, `getListGoalInvitationsQueryKey(id)`, `getListParentFundingGoalsQueryKey()` helpers. After contributions invalidate goals/detail/history, finance accounts/summary/history/filter options and financial plan. Status/edit changes invalidate goals/detail/history and planning; consent changes invalidate invitation and parent funding lists. Refetch on focus/mount and every 15 seconds to observe another actor/session's funding and revocation. Never expose student finance queries on the parent screen. Clear all user-scoped caches on sign-out/account change.

## Deployment and verification

Additive `savings_goals`, `goal_history`, `goal_invitations` tables and nullable ledger `goal_funding_source`/`goal_funding_actor_id` columns were applied to the development database using non-force `pnpm --filter @workspace/db run push`. Existing accounts/transactions were not rewritten. Apply the additive schema before deploying the API. Protected accounts use server-only `type:"goal_reserve"` (not accepted by account-create inputs).

`pnpm --filter @workspace/api-server run test` passes 18 tests, including a new real-PostgreSQL synthetic-owner/parent integration test. It covers owner boundaries, real role checks, consent token hashing/expiry/revocation/retry, restricted parent receipts, positive amounts/JOD precision, duplicate idempotency and concurrent overfund/overspend, available/reserved/net reconciliation, blocked ordinary reserve movements/lookup/request and shared campus lock protection, live savings actuals, manual/goal forecast precedence, no income fabrication, all goal status actions and archive retention. Test fixtures are isolated and removed afterward. `pnpm --filter @workspace/api-server run typecheck` passes. No workflows were restarted.
