## Generated hooks and DTOs

| HTTP | Generated hook | Result |
|---|---|---|
| GET `/scheduled-items` | `useListScheduledItems` | `ScheduledItem[]` |
| POST `/scheduled-items` | `useCreateScheduledItem` | `ScheduledItem` (201) |
| GET `/scheduled-items/{id}` | `useGetScheduledItem` | `ScheduledItem` |
| PUT `/scheduled-items/{id}` | `useUpdateScheduledItem` | `ScheduledItem` |
| DELETE `/scheduled-items/{id}` | `useDeleteScheduledItem` | 204 |
| PUT `/scheduled-items/{id}/occurrences/{date}` | `useSetScheduledOccurrenceStatus` | `ScheduledOccurrenceOverride` |
| GET `/planning/calendar?from=YYYY-MM-DD&to=YYYY-MM-DD` | `useGetPlanningCalendar` | `PlanningCalendar` |
| GET `/planning/forecast?through=YYYY-MM-DD` | `useGetPlanningForecast` | `PlanningForecast` |

`ScheduledItemInput` (full replacement PUT): `{name, amount:{minor,currency}, dueDate, category, kind, notes, recurrence, endDate?, status}`. `kind`: `expense|income|savings`; `recurrence`: `none|daily|weekly|biweekly|monthly|quarterly|yearly`; `status`: `planned|completed|cancelled`; amount positive safe integer minor units in ILS/USD/JOD. `endDate` optional inclusive date, on/after dueDate; omit to clear. Category uses existing `PlanningCategory`. Response adds `id` and `commitmentPolicy:"additional_commitment"`.

**Required UI hint:** “Additional commitment — this adds to your existing monthly plan. It does not replace an existing budget, income, recurring expense or savings goal.” No guessed category-based replacement is provided. To change an existing commitment, edit its original source via the existing planning/profile/goals/family UI rather than copy it into this list.

Recurring series cannot be marked `completed` (`400`); complete individual dates instead. Series `cancelled` explicitly cancels the series, not a payment. Occurrence PUT body `{status:"planned"|"completed"|"cancelled"}` completes/cancels/reopens only that valid recurrence date. Repeating the same PUT is idempotent. Reopening an occurrence does not reactivate a cancelled series. Changing recurrence/dueDate/endDate with existing overrides returns `409`; delete/recreate the series deliberately instead. Updating other fields preserves overrides. Deleting a series deletes its overrides only, never ledger data.

## Calendar / forecast policy

Dates are inclusive, real UTC calendar dates, at most 366 days per request. Forecast `asOf` is server UTC today (cannot be overridden) and `through` must be today or later. Calendar may include past dates. `occurrences` are concrete dates, not invented profile bill dates. `monthlyAllocations` are separately labeled **undated monthly allocation**, with month, covered interval, monthly amount and exact allocated amount. They are assumptions, not bills.

Occurrence fields: `id`, `sourceId`, `source` (`scheduled_item|income|allowance|recurring|line`), `name`, `date`, `amount`, `category`, `kind`, `status`, `recurrence`, `includedInForecast`, `policy`. Source IDs are owner-authorized only. Only scheduled-item occurrences are mutable here; adapt other sources through their original APIs.

Forecast returns `estimate:true`, `label:"Estimated / Projected"`, `policy`, `assumptions`, `assumptionCodes`, `asOf`, `through`, `currencies`, `occurrences`, `monthlyAllocations`. Calendar also includes `assumptionCodes`. Each currency row contains exact-money `availableOpening`, `expectedIncome`, `upcomingExpenses`, `recurringExpenses`, `plannedSavings`, signed `projectedBalance`. Opening is the sum of ordinary owner accounts, **excluding goal reserves**. No FX; unsafe aggregate values fail with 400 instead of truncation.

**Frontend disclosure contract:** Both calendar and forecast return machine assumption code `today_dated_income_may_already_be_in_opening`. Display a localized informational warning: “Income expected today may already be included in your available balance. Ordinary income expectations are not linked to transactions; review the original expectation to avoid counting it twice.” This applies to non-allowance profile income and additional scheduled income. Dates/amounts are never guessed to match ledger postings. Such planned income remains included until its source is updated (or its scheduled occurrence completed/cancelled); it is not a guaranteed new receipt. The human-readable `assumptions` array also includes this warning.

Equation: opening + expectedIncome − upcomingExpenses − recurringExpenses − plannedSavings. `recurringExpenses` contains included concrete recurring expense dates; `upcomingExpenses` contains included one-off expense dates plus undated expense allocations. Completed/cancelled/posted occurrences are excluded. Past overdue items are excluded, with **no automatic carryover**. Today’s posted allowance is already in opening and is never counted again.

* Existing authoritative monthly reconciliation is reused: manual expenses > recurring > housing/commute baseline per canonical category/currency; housing share replaces rent, utilities/internet separate; commute override wins. Budgets never become expenses. New scheduled items are independent additional commitments.
* Winning recurring expense sources use concrete recurrence dates; the corresponding monthly estimate is not added again. Manual expense envelopes and profile baselines are allocated, not invented as monthly bills. Dated manual lines are visible informational markers covered by their envelope, never a second debit.
* Savings uses max(manual savings, active goal monthly requirements) per currency, allocated once; goal requirements are a frozen current snapshot, not a guarantee or automatic contribution. Undated goals have no invented due date.
* Active profile incomes with a date expand from that original anchor; one-time/irregular dated income occurs once. Undated recurring income uses monthly annualization. The exception is recurring manual parent allowance, whose dated markers are informational and whose monthly annualized amount participates only in the inclusive allowance envelope. Raw scholarship metadata is never income; an explicitly entered scholarship income is treated like any other income.
* Parent allowance uses an inclusive per-currency horizon envelope: max(manual recurring expectation, active consented scheduled occurrences), not their sum. Posted occurrences are removed from future schedules; posted amounts within the requested interval reduce the manual envelope before comparison. Only residual manual envelope allocations are added; scheduled/posted coverage reduces monthly slices chronologically. Dated nonrecurring manual allowance is suppressed only for a matching authorized schedule/date/currency (including already-posted occurrences). Failed allowance occurrences remain estimates, not guaranteed payments.
* Revoked/denied family schedules are never returned. The student's own already-posted allowance credits still privately reduce manual allowance expectations after consent removal, because they remain in opening; no revoked parent/schedule identifiers are disclosed.
* Future monthly envelopes are held constant from today’s existing plan. Each calendar month allocates `floor(M*b/D)-floor(M*a/D)` minor units, where D is days in that month and a/b are elapsed-day boundaries of the inclusive slice. This deterministic remainder distribution totals exactly M for a whole month, handles leap years, and never uses floating-point money. No deduction of unrelated historical expenses or promise of future income is implied.
* Monthly/quarterly/yearly recurrence clamps the **original** anchor day to month end (Jan 31 → Feb 28/29 → Mar 31), honors inclusive end dates and never drifts after February.
* Allowance recurrence follows the actual worker cursor, not a reconstructed start-date series. The first date is persisted `nextPayment` even if off-anchor. Weekly/biweekly advance from that actual date; monthly advances to the next month using the original `startDate` day and the worker's `nextAllowanceDate` helper. Example: weekly start June 1 / next June 3 gives June 3, 10, 17; monthly start January 31 / next February 3 gives February 3, March 31, April 30. Inclusive end dates retain that first off-anchor payment. Manual allowance coverage uses these exact dates.
* Calendar/forecast financial reads share one repeatable-read transaction: profile, manual/recurring plan, budgets, allowance projections/posting status, goal requirements/reserve holdings and available opening. A concurrent contribution cannot combine an old savings requirement with a newly reduced opening. Legacy `/planning` formulas and default goal API transaction behavior are unchanged.

Refresh calendar, forecast and scheduled-item queries after scheduled mutations and after source/profile/planning/goals/finance/family changes; opening and allowance posting can change independently. Existing monthly plan is not modified by new scheduled items. Errors follow existing sanitized `{error:{code,message}}` handling: invalid inputs/range 400, unauthenticated 401, wrong role 403, non-owner/missing item 404, unsafe anchor change 409.
